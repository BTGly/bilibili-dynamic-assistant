# 第一批：自动参与正确性修复

## 计划与实施范围

1. 将三连参与改成串行执行；网页、自动任务与两个命令行入口共用账号文件锁。
2. 将活动失败隔离为暂缓或待核查；账号限流、登录与验证异常暂停账号队列，保留原因。
3. 写请求开始前保存 `in_flight`，每步结束后保存成功、失败或未知结果。进程中断后不把未知写请求当成未执行。
4. 核查后才能恢复失败目标；成功动作不再提交。历史日志中已确认成功的动作也会继承，历史失败记录默认待核查。
5. 按保存的规则执行必需动作，收藏不再默认必需。转发抽奖旧记录缺少规则时进入待核查；后续详情抽取保存 `need_follow / need_repost / need_comment`。
6. 纠正取消与失败混淆，显示部分完成、待核查、账号暂停和用户取消。

## 持久化与恢复

- 新增 `participation_guards` 表，按账号、活动隔离。空活动 ID 代表账号队列状态。
- 动作进度独立于最多保留 500 条的历史日志，日志清理不会删除动作进度。
- `review`、`deferred`、`excluded` 都不能进入自动候选。此版采用人工核查恢复，不设置自动到期重试。
- 有限页数的转发、评论查询未找到结果，不能证明请求失败。未知结果必须提供人工核查结论，不能直接重发。
- 写请求不做内部重试。取消只在动作边界停止；已发出的请求仍按返回结果保存，不表示撤回。
- Windows 使用字节文件锁，其他平台使用 `flock`；进程退出由系统释放锁。锁文件位于用户数据目录的 `data/write-locks/`。

## 网页与接口

- 活动旁可“排除”；隔离活动显示原因及“核查恢复”。恢复未知动作时要求逐动作确认成功或失败，并填写依据。
- 账号暂停后显示提示及恢复入口。恢复账号不会同时恢复隔离活动。
- `GET /api/participation/guards` 查看账号状态和活动进度。
- `POST /api/participation/guards/{dynamic_id}/exclude`，请求体 `{"reason":"人工排除原因"}`。
- `POST /api/participation/guards/{dynamic_id}/release`，请求体示例：

```json
{"evidence":"已核查本人动态与评论", "resolved_actions":{"repost":"succeeded","comment":"failed"}}
```

- 恢复账号使用 `{dynamic_id}=account`；核查结论仅能更新已有未知动作，不能改写已确认成功的记录。
- 旧转发活动应先刷新详情取得规则，再填写核查依据恢复。仅点击恢复不会补齐缺失的规则。

## 验收

测试覆盖：活动失败后不再入选、账号异常停止后续目标、成功动作保存与跳过、超时及崩溃后的重复提交拦截、人工核查后的续执行、取消保留进度、可选收藏失败不影响完成、Windows 跨进程锁。

测试收集前使用临时数据目录，每项测试自动隔离。数据库引擎在路径越过测试隔离目录时直接中止，检查发生在创建目录与连接数据库之前。

本批不修复开奖日期、不迁移已有推断日期、不修改诊断包与凭据权限，也不做提速。验收未向真实账号提交操作，平台规则与接口变动仍需后续受控实测验证。


验证结果：后端全量 447 项通过、2 项跳过；最终账号保护与状态调整相关回归 49 项通过。前端 10 项测试通过，TypeScript 检查及生产构建通过，`web/static/dist` 已更新。
