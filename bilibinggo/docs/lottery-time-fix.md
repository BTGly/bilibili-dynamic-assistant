# 第二批：开奖时间与旧数据修复

## 范围与执行顺序

本轮包含源码修改、隔离测试，以及用户授权的真实 SQLite 备份和修复。实测文档作为问题证据；不把其中的操作建议当作额外授权。

1. 统一时间模型，删除缺失时间补半年行为。
2. 分开开奖时间与参与截止时间，保存原文片段和精度，验证抽取结果。
3. 接入入库、状态、列表排序、提醒和参与保护。
4. 生成只读旧数据预览，隔离测试通过后备份并按预览修复。
5. 对照备份验证非目标活动、参与记录和逐动作进度没有变化。

## 时间语义

- `lottery_time` 为可空开奖时间；`conditions.participation_deadline` 单独记录参与截止时间。
- 对应的 `*_evidence`、`*_precision` 和 `lottery_time_source` 保存在 conditions 中。平台时间保存接口字段来源；转发原文日期要求字面片段存在、语义匹配、解析日期一致。
- 无年份表达需要动态发布时间作参照；不支持或有歧义的相对时间保持未知。抽取缓存版本更新，重新使用缓存也须验证原文依据。
- 日期精度只显示日期，不展示虚构的 00:00；状态转换使用次日零点作为该日期结束边界。开奖与截止互不代替。
- 显式推断标记的时间对所有消费者均视为未知；旧的相对时间或缺年份文本不能按入库时间补年份。原始旧文本保留为 `legacy_lottery_time_text`。
- 完成抽取但没有时间的记录保留 `time_extraction_checked`，不会仅因时间未知就反复触发详情补全。刷新与缓存转换保留人工核查、修复审计及平台状态来源；带推断标记的旧缓存保留活动本身，但不能恢复合成日期。
- 未标记的历史数值日期保留，界面提示原文依据未保存；本次不凭猜测批量删除它们。

## 状态与参与

- 未知时间显示 `draw_status=unknown`，默认待审核，清除旧提醒标签。
- 截止后停止参与，显示已截止；已有参与记录保留已参加。平台明确结束状态仍有效。
- 网页支持“核查时间”，要求记录依据，选择人工参与或继续待审核。人工批准不补日期，不进入自动候选；网页与命令行共用参与前检查和账号执行锁。
- 既有失败隔离继续生效；时间批准不自动解除其他失败隔离。
- 按开奖时间排序时，未知值在升序和降序中均置后；未知时间不产生开奖提醒。

## 修复工具

默认仅只读 SQLite，不通过有状态回写行为的业务加载器生成预览：

```powershell
.\.venv\Scripts\python.exe scripts/migrate_lottery_times.py --database data/binggo.db --preview docs/reports/lottery-time-repair-preview-2026-10-09.json
.\.venv\Scripts\python.exe scripts/migrate_lottery_times.py --database data/binggo.db --preview docs/reports/lottery-time-repair-preview-2026-10-09.json --apply --backup data/backups/before-time-repair-2026-10-09.db
```

只处理根字段或 conditions 中 `lottery_time_inferred` 严格为布尔 True 的记录。有可信来源或原文证据冲突时跳过。先用 SQLite online backup 备份（包含 WAL 内容）并检查完整性，再在单个事务中校验全部目标指纹。预览过期则整体退出，不部分修改。

修复清空合成时间及文本，移除推断标记，保留修复审计信息，重算目标状态。参与记录、逐动作日志、凭据和非目标活动不在更新范围。再次运行预览应无剩余无冲突推断记录。

## 验收

回归覆盖未知时间不生成日期/提醒/自动候选，原文截止不能当作开奖，证据与日期一致，日期精度状态边界，人工批准不造日期，缓存不丢失推断标记或平台来源，以及只读预览、备份、目标修复、过期预览回滚与证据冲突跳过。

实际修复及验证结果见 `reports/lottery-time-repair-result-2026-10-09.json`。

2026-10-09 执行结果：566 条活动中修复 50 条无来源冲突的明确推断日期；44 条转为待审核，6 条保留已参加。其余 516 条活动与所有其他数据库表内容均与备份一致。原库和备份完整性检查为 ok；修复后无剩余推断标记。备份位于 `data/backups/before-time-repair-2026-10-09.db`。
