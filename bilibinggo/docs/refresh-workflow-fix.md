## 检查点与恢复规则

- 已分类但未完成的目标保留分类检查点。超过 5 分钟后，恢复时重新读取原文和平台详情，不沿用旧公告状态。
- 单条分类或详情异常暂缓；第一次冷却 5 分钟，第二次 10 分钟；第三次失败进入待核查，停止自动重试。分类成功的检查点可供详情重试复用。
- 即使所有数据源容器都没有变化，也处理已到期的待处理项；不依赖下一次出现新专栏来恢复。
- 非抽奖、充电等明确跳过结果不会每次重新分类。需要重新核查的跳过记录可通过 CLI 显式恢复。
- B 站限流、验证、登录失效等账号异常暂停读取队列并保留账号保护状态，需要在现有账号核查入口解除；LLM 服务异常只暂缓对应目标。
- B 站 412、429、限流业务码不再在同一次请求内部反复重试。已发出的详情请求仍需收尾；停止新操作不能撤回已发出的请求。
- 取消详情阶段时，收集并保存该批已经发出的请求结果，再结束任务；取消分类阶段时已保存的分类检查点继续保留。

设置页新增“刷新待处理与核查”列表，显示目标、状态、失败次数、重试时间和原因。恢复必须填写核查依据；执行任务期间不能改动检查点。

API：`GET /api/refresh/checkpoints`；`POST /api/refresh/checkpoints/{dynamic_id}/release`，正文为 `{"evidence":"核查依据"}`。正式任务使用 `POST /api/jobs` 的 `refresh_links` 动作。

## 正式 CLI

在项目目录运行：

```powershell
# 查看缓存数据源中的新目标与待核查记录；不发出 B 站/LLM 请求
.venv\Scripts\python.exe scripts\refresh_links.py --source DS-7 --chunk 20 --limit 100

# 实际处理，写入统一任务历史；已有任务时拒绝撞车
.venv\Scripts\python.exe scripts\refresh_links.py --source DS-7 --chunk 20 --limit 100 --execute

# 无需重新检查数据源，续跑已登记目标
.venv\Scripts\python.exe scripts\refresh_links.py --execute

# 人工核查后恢复指定检查点；提供真实动态 ID
.venv\Scripts\python.exe scripts\refresh_links.py --release 1234567890123456789 --evidence "已核查页面恢复" --execute
```

默认只预览；初始化会创建缺失的数据库表。Ctrl+C 请求取消，并等待在途请求收尾。正式入口替代项目外 `run_source_chunked.py` 的分块能力，不再硬编码真实数据库路径，也不在账号异常后继续下一块。外部旧脚本保留兼容，后续使用上述正式入口。

任务锁和限流按同一用户数据目录共享；使用不同 `BINGGO_HOME` 的进程不能互相协调。`BILI_RPS` 保留现有默认 3，不代表已证明的安全频率；显式设为 0 仍表示关闭限流。多个进程配置不同时，活跃期间采用较低频率，空闲 60 秒后按新进程设置重新开始。

## LLM 边界

连接 10 秒、读取 90 秒、发送 20 秒、等待连接池 5 秒。仅连接失败和指定服务端临时错误允许最多两次请求；重试等待最多 5 秒。读取、发送、连接池超时不自动重发。对同一份损坏 JSON 不再重复解析并等待；输出截断明确报错，不当作完整抽取结果入库。

实现参考 HTTPX 官方的[连接池与清理说明](https://www.python-httpx.org/advanced/clients/)和[四类超时说明](https://www.python-httpx.org/advanced/timeouts/)。这些超时限制分别作用于请求阶段，不是整轮刷新任务的总耗时上限。
